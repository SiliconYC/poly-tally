# 历史重建：传输下界、四种重算与可复现实测

## 先说结论

**未来“重新算统计”不应等价于“再次下载全部历史”。** 把不可变原始对象、规则相关
计算缓存、发布统计分成三层，才是最有把握的数量级优化。冷全量则必须同时削减
工具往返、重复树展开与解析工作；仅提高并发不能承诺 100 倍。

本页的离线基准不改采集器、不联网、不新建 Key、不修改原 capture、数据库或其终端。
当前连接器没有经验证可用的任意私有仓库 clone/pack 传输入口；本地 pack 试验
**不等于已经通过连接器完成 Git clone**。不会从 API JSON 伪造 commit 对象。

## 2026-10-21 实测：明确是部分捕获，不是最终全量

观察窗口 **14:13:37.064892—14:13:38.337054 UTC**；冻结 manifest、文件清单和各文件
字节至内存，后续新增文件不进入此次分析。它是有记录的观察窗口，不是运行中采集器的
原子事务快照。输入清单摘要：
`e6fbc099cc2bbc63590dc8a3191058959eac9e82faefc5e1ec4db0fcc4fd8134`。

16 个仓库的第一父链均已到根，13 个仓库物化完整；另 3 个仍在采集。
已知缺失 1,921 个 tree 入口、3,797 个合格 blob；未知子树可能继续发现对象，
**这些缺口不是剩余总量的上界**。以下全部是单轮本地测量，操作系统缓存不受控，
不是物理磁盘冷读，也不是网络/统计引擎端到端 A/B。

| 项目 | 实测 |
| --- | ---: |
| API commit 元数据 | 2,300 个 / 2,810,624 JSON 字节 |
| 已捕获且 SHA 校验通过的 tree | 7,137 个 / 11,965,654 JSON 字节 |
| 已捕获且 SHA 校验通过的 blob | 2,104 个 / 23,239,675 JSON 字节 |
| tree 原始 Git 对象体 | 2,206,809 字节 |
| blob 原始字节 | 16,956,234 字节 |
| 冻结输入读取（包含 timing） | 1.272 秒 |
| 冻结后的全部已存对象验证 | 0.687 秒 |
| 对象验证 + 可达图/路径规则/剪枝分析 | 2.699 秒 wall / 2.693 秒进程 CPU |
| tree/blob 实测 pack | 9,241 个对象 / 5,962,225 字节 |
| 临时 loose 对象准备 / pack 生成 | 1.005 秒 / 1.913 秒 |
| pack index / 解包并逐对象 SHA、字节复核 | 0.198 秒 / 0.170 秒 |
| API commit JSON 的额外 zlib sidecar | 570,407 字节；不是原始 commit |

pack 采用 `git pack-objects --window=10 --depth=50 --threads=1 --delta-base-offset`，
输入真实已校验 tree/blob，输出在独立 `0700` 临时目录；用另一空 bare 对象库索引并
解包核对每个对象，最后删除临时目录。没有 commit、refs，也缺少规则排除的 blob，
所以它**不是可 clone 的完整仓库**。参数控制 delta 搜索窗口和深度，取值影响体积与
CPU，见 [Git pack-objects 官方说明](https://git-scm.com/docs/git-pack-objects)。

这组已知子集的 tree/blob JSON→pack 字节比为 **5.90 倍**，raw→pack 为 **3.21 倍**，
不是 100 倍。pack 是批量传输规模的实测代理，**不是完整 pack 的数学字节下界**：
后续对象既会增加数据，也可能提供更优 delta 基，压缩大小不能简单单调外推。

### 时间到底耗在哪里

同一冻结输入有 6,168 条逐工具 timing：

- 树工具 3,919 次，均值 0.468 秒、P95 0.699 秒；blob 1,771 次，均值 0.412 秒、
  P95 0.635 秒；递归树 462 次，均值 0.489 秒。
- 样本从最早开始到最晚结束跨度 2,901.905 秒；所有已记录工具运行区间的**并集**
  653.387 秒；其余无工具记录空档 2,248.518 秒。
- 空档可能包括规划、JSON 编解码、持久化、工具编排、调度与暂停，**不能全部叫网络
  耗时，也不能凭此归因某段代码**。工具时间之和 2,799.521 秒含并发重叠，不能再当墙钟。

下一次运行应分别记录 `discover / plan / tool queue / tool active / serialize / write /
validate / parse / aggregate / publish`；用同一 manifest 与输出完整性证明比端到端
耗时。不能用局部 pack 解包的 0.170 秒除整次抓取跨度，冒称总流程已提速上万倍。

## 四种操作必须有不同成本

| 情景 | 必要远程对象读取 | 必要本地工作 | 复用与失效边界 |
| --- | --- | --- | --- |
| 真冷全量：原始对象也没有 | 取完整第一父链、需要的树与合格 blob；末尾核对引用 | 校验对象，解析唯一有效 blob，重建全部快照 | 不能用旧规模、旧时间戳冒充新采集 |
| 仅清统计，保留原始对象 | 固定历史重放为 **0 次**；若声称“最新”，仍需重新发现和核对 refs | 从空统计库重建；可选择不复用任何解析结果 | 原始内容不是旧统计；但当前 epoch 的“禁止旧对象缓存”约束仍须遵守，不能静默改义 |
| 规则变化再算 | 原对象覆盖新规则时为 0；扩展收录范围/大小上限时仅补新缺对象 | 重判路径；仅重算失效 `(blob, language, parser/version)`；生成新规则快照 | 不把旧规则指标混入新规则；只缓存“当时合格 blob”并不保证任意未来规则可离线重建 |
| 正常增量 | 新 HEAD 前缀之外的缺失 commit/tree/blob；不变时对象读取 0 | Merkle 树差分、增量解析、追加/替换受影响历史 | force-push/回退先找有效公共前缀，撤销失效尾部；旧内容对象仍可复用 |

固定离线重放的成功时间只能表示“此时完成计算”，不能把旧 capture 的观察时间更新为
“现在已核对远端”。新 epoch 的空统计库与可否复用原始对象应成为**显式不同选项**，
本页不改变现有 epoch 重置契约。

## 严格调用数、字节与 CPU 下界

记 `C_r` 为仓库 r 的第一父提交数，`T` 为所选契约要求的唯一树集合，`B` 为所有历史
路径规则命中的唯一可读 blob 集合，`M_T/M_B` 为其中本地缺失部分。身份按对象类型+SHA
去重，路径资格不能仅按 SHA 判定。`I/H` 分别为实际发现/元数据及引用核对调用数，
`P/F` 为提交分页及缺口回退调用数。以下是方法条件下的下界，不是未测网络速度。

### 单对象连接器

在当前“所有子树均取证”的非递归树契约下，无重试的成功调用数为：

```text
N = I + H + P + F + |M_T| + |M_B|
P >= sum_r ceil(C_r / 100)            # 每仓独立列表、无跨仓已知提交复用时
```

提交列表可能混入第二父可达提交，分页也需要连续性核验，不能把该信息下界当作必然可达
的调用数。当前样本该下界是 33 页，不是 2,300 次逐提交请求。列表 API 支持的分页参数
以 [GitHub commit 列表文档](https://docs.github.com/en/rest/commits/commits#list-commits) 为准。

只要 blob 入口仍然一次一对象，`|M_B|` 次成功调用就不可由“更聪明的树算法”消除。
令最大并发为 `p`，第 i 个实际调用占用时长为 `l_i`，依赖链总占用时长为 `D`，
有效带宽上限 `W`，实际传输字节 `X`，则任何调度都有：

```text
wall >= max(sum_i(l_i)/p, D, X/W)
```

均值不是最小延迟，不能把样本均值直接代入称“严格下界”。仅作容量估计：已知 5,901
个合格 blob 若全冷、每个 0.412 秒且 6 并发，即使无其他工作也约 **405 秒**；
这是基于实测均值的模型估计，尚未包含未知子树、树调用、限流和失败。

### 字节与 CPU

- 对给定 blob 集合，非压缩 base64 内容至少 `sum(4*ceil(size/3))` 个 ASCII 字符，
  另加 JSON 封装。HTTP 压缩可能降低线上字节，因此不能把 JSON 文件体积当抓包字节。
- 要独立核验原始 blob/tree SHA，至少读取并散列所有需验证对象的原始字节，CPU 工作
  为 `Ω(sum blob bytes + sum raw tree bytes)`。本轮已存集合至少有 19,163,043 字节
  待散列，未包含缺失对象或 API commit 元数据处理。
- 对新的解析语义，不可能在不读内容的情况下给任意输入精确行数：最坏情况下也是
  `Ω(sum uncached eligible blob bytes)`；已验证且版本相同的派生指标可以跳过解析。
- 至少处理 `Ω(C)` 个提交身份/时间；若必须输出每个提交快照，则输出本身也有相应下界。
  树差分的目标是 `O(唯一 tree/路径上下文 + 变更条目)`，不是逐提交整树 `O(C×文件数)`。
- **没有测得普适“理论最快秒数”**：真正秒数还取决于带宽、散列/解析吞吐、磁盘、服务端
  限流和依赖图。此处本地 cache 未受控，1.272 秒读入不构成磁盘下界。

## 树策略：根递归、Merkle 差分与有证明的剪枝

### 1. 在合适的根/子树使用 recursive，而不是所有提交盲目整树

本轮 2,300 个提交有 2,271 个唯一根树；所有 pinned HEAD 合计可见 1,775 个唯一树，
全历史已知可达树身份 9,058 个（其中一部分缺失）。只取 HEAD 不能重建历史删除的文件。

可先对覆盖面大的未知根请求 recursive，若完整则重建所有直属 tree 字节，逐个校验
SHA 后入全局对象库；其余历史仅补未见对象。成功递归调用数记为 `Q`、剩余非递归缺树
记为 `T'`，则树调用由 `|M_T|` 改为 `Q+|T'|`，**blob 调用不变**。重复根或相同子树
应当直接复用；对比两树 SHA 相等就整支跳过，否则只下降不同条目。

GitHub recursive tree 有条目/大小限制，必须检查 `truncated`；服务端限制目前为
100,000 条或 7 MB，连接器还可能有更小的返回限制。失败/截断时回退到非递归分片，
不得把缺失条目当空目录，见 [GitHub tree 文档](https://docs.github.com/en/rest/git/trees)。

### 2. 统计所需闭包剪枝：下一阶段设计，本次未启用

当前导入契约要求所有子树字节完整取证，**本次基准不改变此契约**。若另设“仅统计所需
闭包”模式，可使用一条保守、可证明的规则：仅当普通 `exclude` 模式形如 `Q + '/**'`，
且现有 glob 语义下目录完整路径 `D` 匹配 `Q`，则任意后代 `D + '/' + s` 必被排除。
普通 exclude 优先且不可由 include/source_preserve 覆盖；其他模式一律不剪。

在父 tree 已校验后，记录子 tree SHA 引用、完整路径上下文、规则版本和排除证明，
而不下载其子树。**证明的是该路径不影响统计，不是验证了排除子树的原始字节**。
同一个 SHA 以后出现在合格路径，或规则变化使证明失效时，必须恢复下载。

本轮已知图中可省 **662 / 7,137 = 9.28%** 个已捕获唯一 tree，约 1,688,072 JSON
字节 / 413,999 raw 字节；另避免 12 个已知缺失子树入口。未知后代收益未猜测。
这是有价值的优化，但此样本不支持“仅剪枝就 100 倍”。

### 3. 同源不等于相同 Git 对象

三成员同源组在当前部分图上：commit 仓库内计数之和/全局唯一都是 1,756；合格 blob
之和 3,848、全局唯一 3,798，仅省 50 次；tree 之和 5,938、唯一 5,912，仅省 26 次。
因此本轮跨仓同 SHA 去重不是大头。内容相似仍可能利于 pack delta，但不能拿业务上的
“继承链”当成同提交或同 blob；统计同源合并规则与传输去重必须分开。

## 100 倍级目标怎样才可证实

1. **先阻止重复冷启动**：保留受保护、可重验的原始对象库，清统计不清对象。
   固定历史重放可从数千对象调用降为 0；但“网络对象调用减少 100%”不自动等于
   “全流程 100 倍”，最终仍要加上验证、解析、快照生成与发布。
2. **再消除逐对象交互税**：受支持的 Git 授权环境或官方批量对象通道，在正常权限内
   使用 Git pack/fetch，批量 `cat-file --batch` 读取。当前连接器没有可用 clone/pack
   入口，不能猜凭据、转发 token、借 Sites 源码代理绕过。可配置正常 GitHub 连接的
   执行环境属于未来方案，**此次未验证其私有 clone 可用性或端到端时长**。
3. **不能只建议 partial clone 就结束**：`blob:none` 延迟 blob 下载，而不是取消最终
   需要的 blob；若后续命令逐个触发懒下载，又回到 N+1。必须测量服务器支持、按批补全
   与完整第一父链。也不能使用 shallow clone 破坏历史完备性。
   参见 [Git clone 过滤语义](https://git-scm.com/docs/git-clone.html)。
4. **用 Amdahl 定律约束承诺**：若只优化占总时长比例 f 的部分，该部分提速 s 倍，则
   总体最多 `1 / ((1-f)+f/s)` 倍。要总流程 100 倍，即便那部分无限快，未优化部分也必须
   少于 1%。所以传输、规则匹配、验证、解析和逐提交聚合必须分别测。
5. **验收用同一固定输入与同一输出**：分别报告冷对象/暖对象、冷解析/暖解析、远端引用
   是否重新核对；旧/新结果逐提交相等；多次测量报中位数和范围。若旧基线 3 小时，
   100 倍门槛是 108 秒；这是条件示例，不是本次已测旧基线。

当前证据说明已知原始对象不是“本质上需要几个小时的数据量”，但**没有证明当前通道
冷全量已达到 100 倍**。局部 5.90 倍压缩、9.28% 剪枝、0.687 秒已存对象校验都不能
替代端到端的完整数据验收。

## 缓存设计的安全与可重建性

- **L0 不可变对象/证据库**：blob/tree 按对象类型+SHA，并保留 API 身份、第一父链、
  捕获来源与原始观察时间。私有数据 `0700`，与源码和公开发布目录隔离；内容对象仍需
  校验。仅 SHA 不证明授权，不能把一个用户/授权域的对象命中暴露给其他域。
- **L1 计算缓存**：路径判定依赖 `(tree SHA, 完整路径上下文, rules version)`；内容指标
  至少依赖 `(blob SHA, language, parser/version, 影响指标的规则)`。不使用仅 tree SHA
  的资格缓存，也不把路径不同导致的语言改变漏掉。
- **L2 统计与发布**：按 epoch/规则/有效 HEAD 链隔离，可随时从空库重建，完成验证后原子
  切换。L0 命中不能复活被明确撤下的旧规模，也不能伪装新鲜远端观察。
- 若保留的只是当时合格 blob，未来规则扩展时须补缺；如果源仓库已删除且未保存新需要
  的字节，则无法完全重算，应明确不完整，而不是补零。不要把短期 CI cache 当永久备份。
- 原始私有对象不可上传公共 artifact、数据分支、日志或文档；本页只含聚合数。清理仅对
  明确可恢复的临时副本执行；长期对象库需独立 retention/备份策略。

## 复现

```bash
# 配置必须与要评估的规则相符；capture 要在源码目录外且权限符合契约。
python scripts/bench-history-transport.py /private/capture \
  --config /private/capture/config.snapshot.json --pack > /private/aggregate-benchmark.json
python -m pytest tests/test_history_transport_benchmark.py -q
```

脚本输出没有私有仓库名、路径、commit/tree/blob SHA 或源码；只保留聚合数与输入清单摘要。
报告的 `capture_complete` 是本地 manifest 声明和已知对象覆盖状态的检查，**不是正式导入、
新鲜发现或最终发布完整性证明**；请仍运行正式导入器。数据继续抓取时，新一轮报告输入
不同，不能直接拿两个不同集合的时长比作为算法加速比。

测试覆盖真实 Git 对象、跨仓共享身份、路径敏感排除、缺失 blob、损坏 blob、symlink
拒绝、冻结后新增文件不被读取、只读原 capture、真实 pack round-trip 及时间区间并集。

计算引擎的 Merkle/路径匹配优化、冷统计与增量三场景等价基准见 [历史重建计算优化](history-rebuild-compute.md)。
